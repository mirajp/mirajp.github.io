# Decision 0.4a: Persistent map for `SvgDocument.nodes`

## Benchmark

Run from the repository root with:

```sh
node --expose-gc spikes/svg-editor/persistent-map/bench.mjs
```

The script installs pinned `immutable@5.1.9` and `hamt_plus@1.0.2` packages into a temporary directory, removes that directory on completion, and does not change the repository dependencies. First run requires npm registry access.

**Machine:** Windows 11 / WSL2, Ubuntu 24.04; Linux `6.18.40.1-microsoft-standard-WSL2`, x86_64; 13th Gen Intel Core i7-1355U, 12 logical CPUs. **Node:** v24.19.0.

Each record has the contract's element-node shape (`kind`, `id`, `tag`, `attrs`, `style`, `children`, `parent`). Measurements use 31 single-update samples, 25 batches of 100 sequential updates, 9 retained-version memory samples (200 versions each), 21 complete iterations, and 31 batches of 10,000 lookups. ## Recommendation

Use Immutable's `Map` behind the `PersistentMap<K, V>` contract. Both HAMT implementations make updates and retained history inexpensive compared with object spread, and either easily meets the single-update frame budget at 50,000 nodes. `hamt_plus` was faster in the 50,000-node multi-update, iteration, and lookup measurements, but its edge is not important for the primary one-node command path. Immutable's more familiar API/ecosystem and slightly lower retained-version memory make it the lower-risk production dependency. Do not use a plain object for versioned node storage.

## Contract adapter and risks

Add a small wrapper implementing `PersistentMap<K, V>` around `ImmutableMap<K, V>`: expose `size`, `get`, `has`, `set`, `delete`, and `entries`; have `set`/`delete` return wrapped new maps and never expose mutable/transient APIs. Convert `entries()` to the contract's `IterableIterator<[K, V]>` if the library's iterator typing does not match exactly. Keep the concrete library type out of `SvgDocument`.

Benchmarks are process-, heap-, and workload-sensitive; the reported memory is V8 heap delta, not resident set size. Iteration order is implementation-specific and must not become serialized attribute/node ordering. Production dependency/version approval remains separate; the temporary benchmark installation is not a dependency change. A future decision should repeat measurements under CI's Node version and representative real documents before setting regression thresholds.
